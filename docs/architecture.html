Locus: architecture

High-level decisions that serve intent.md. These are expected to change. Details belong in the code.

This is the target design. On 2026-10-31 the backend decision was reversed: the plan to keep Urbit for identity only and rebuild on Rust, SQLite and iroh is dropped. Urbit is the backend, and a ship runs on every client. The primitives below are built in the %store agent (desk/app/store.hoon), with the interface in ui/. status.html says what runs today.

Decisions

  1. Clan identity. Each clan has one Urbit planet as its root identity, with one administrator. The planet runs on a server. Other servers and devices are moons of it, so every client runs a ship.
  2. Server stack. NixOS for a declarative system with rollback, ZFS for snapshots, and Urbit ships for the clan's state. Software that does not belong in a ship runs beside it on the same machine. Heavy software (AI inference, games, 3D, video) runs on the host and is launched through Locus operations.
  3. Data. Everything is built from six primitives, listed below. They live in ship state, with large blobs on disk beside the ship.
  4. One action layer. Every action is an operation. Keyboard, mouse and agents all call the same operations. Permissions are per member and per agent, and everything is audited. An agent's proposal is a branch of unapplied operations, reviewed as a diff.
  5. Safety. Deletions and overwrites can always be recovered (the operation log, ZFS snapshots). The exception is an explicit purge, for something like a leaked password. Changes to the operating system need a human's approval and can be rolled back.
  6. Sync. Every object has one home server, which orders its operations and checks their permissions. Client ships keep a partial copy, apply operations at once, then replay them on top of the server's order. They keep working offline, but their changes stay provisional until the server accepts them, and devices do not sync with each other directly. A conflict keeps both versions. Nothing is ever silently overwritten. Text bodies use a CRDT, because a person and an agent will often edit the same one at once.
  7. Interfaces. Being redesigned from first principles. The earlier point-and-click design was a placeholder and is discarded, and the shells (libcosmic on the desktop, iced in the browser) are no longer assumed. An interface talks to the ship on its own device. Android comes later.
  8. Components. Small parts that each do one thing. Outside code is taken as hard forks of small pieces, never as soft forks of large projects.
  9. Distribution. Locus ships as a Nix flake. A clan follows upstream or points at its own fork. Every update can be rolled back.
  10. Feedback. A request carries its context (app, version, recent actions), becomes an issue, an agent drafts a change and a preview, and the administrator approves it before it ships.
  11. Reachability. Clans and devices reach each other over Ames. A relay or tunnel is an acceptable pipe, but never a place where data is stored or identity is managed.
  12. Gateway. A small host process serves the browser app and blobs over HTTPS and WebSocket, so the browser sees one origin. It checks every request against the clan's permissions.

Data primitives

PrimitiveWhat it is
ObjectA stable ID, a type, fields and an optional body. Notes, meetings, people, photos and messages all have this shape. Names and locations are fields, so renames and moves break nothing.
TypeDeclares an object's fields, its operations and how concurrent edits merge. Types implement shared traits such as timed, located or titled.
OperationThe only way anything changes. The log of operations is the source of truth. An entry records who acted, on whose behalf, what they intended and the resulting change.
ReferenceA pointer to an object's ID, in a field or inline in text. It can pin a version. The graph is an index built from references.
BlobImmutable bytes addressed by BLAKE3 hash. An object points to them.
ViewA live query over the rest. It is derived and can always be rebuilt. A reaction invokes a tool when the set of objects in a view changes. What reactions write cannot set off another reaction, so they always end.

A tool is an object too: a JSON program in a small language with no unbounded loops, run by the ship with a fuel limit. It can only produce operations, it declares what it can do, and that is checked statically. When the agent does the same kind of thing twice, it writes a tool and offers it as a proposal. From then on the request runs without a model.

Members, agents and permissions are ordinary objects, so changing a permission is an audited operation.

  • Reactions propose by default. Policy can let one apply automatically, per operation and per actor. Sending a message always needs approval.
  • A reference to another clan's object is a cached copy kept current by a subscription, and its staleness is visible.
  • Agent permissions are the intersection of the agent's own and those of the person who invoked it. An automation with no invoker runs as a named agent with its own grant.
  • An operation's signature is separate from its implementation, which can be code, an agent, or code with an agent fallback. Policy answers two questions: may this actor invoke this operation on this object, and which implementations may it use, by model and effort.

Formats

A format is used internally only if it adds no structure the primitives have to work around. Everything else is a compatibility layer.

  • Internal: HTML for text, ship state, BLAKE3, and media and documents as their original bytes.
  • Import and export only: Markdown, iCalendar and JSCalendar, vCard and JSContact.
  • Generated: JSON Schema, for agent tools over MCP. Types use our own definitions.

A text body is a tree of blocks with stable IDs, written as HTML: 

<h2 id="b1">Prep for Tuesday</h2>
<p id="b2">Confirm the room with <a href="locus:01J…">Lauren</a>.</p>
<img id="b3" src="blob:…" alt="Floor plan">

The CRDT holds the tree, and agents read and write HTML. Bodies are a strict subset: semantic elements, tables, images, MathML and sanitized SVG, with no scripts, styles or event handlers. This is enforced on every write.

Interactive pages are a separate type. A page object holds full HTML as a blob and renders in a sandbox with no network or Locus access. It can only request operations, which go through the normal permission check.

Compatibility

  • Export is a View that renders objects into a foreign format.
  • Import is a batch of Operations, so it is attributed and can be undone.
  • A live file mount for legacy tools is both.
  • A lossless archive (the full log and blobs) is the backup and migration format. Interoperable exports (.html, .md, .ics, .vcf) declare what they drop.

Where the build differs from this design

  • Text conflicts are per block, not a CRDT. A stale write is kept as a clash for a person to resolve.
  • A client ship keeps a full copy of the metadata, not a partial one, and follows one home ship.
  • The host states which actor is calling, and the browser's access to it relies on Tailscale. It has no login of its own.
  • A comet cannot have moons, so a client ship is a member its home allows, until the clan has a planet.
  • The model-written path for tools has not been tried with a real model. The heuristic path has.

Open questions

  • What else must run on a client beside its ship, and how are they supervised together?
  • How does a ship run on a phone, and what does it cost in storage, memory and battery?
  • How do large blobs move between ships? Ames may be too slow for them.
  • How are ships backed up? A restored ship with an old event log cannot simply rejoin the network, so ZFS snapshots alone are not enough.
  • Should the app layer move to %gnat once it is published?
  • Which HTML engine renders pages on the desktop, and do the shells change?
  • Which runtime should serve local AI inference?
  • Are tasks still lines of text inside notes, or their own objects?
